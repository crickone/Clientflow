# Campaign Engine — Slice 2: the Funnel (landing page + form → attributed leads) — Design

**Date:** 2026-08-19 · **Status:** APPROVED
**Builds on:** Slice 1 (the Campaign Kit — live). **Decision locked:** the form is **"Register your interest" → a campaign-attributed lead** (name + phone + email + optional message; the gym follows up by phone — matches the no-pricing/enquire house rule).

## Goal

Every campaign gets a **branded landing page** on the client's own site with a **"Sign up now / Register your interest"** form. A submission creates a **lead attributed to that campaign** (`leads.campaign = "Summer Shape Up 2026"`), landing in the pipeline's entry stage and instantly filterable on the board's campaign segment. The landing page is generated as a campaign asset (same Approve / Go-again flow), goes live on Launch, and its branding comes from the tenant's own settings.

## Non-goals (Slice 3 / later)

- Seasonal calendar + daily-brief "are we ready?" radar + the CFA scoreboard (Slice 3).
- Pixel-matching the client's bespoke imported HTML (we match via the tenant's brand *tokens* — see Branding).
- Payment/booking/checkout on the page (it's a lead-capture form; price is a phone call).
- A/B variants, custom domains per campaign (uses the site's existing host), analytics beyond the signup count.

## Architecture (assembles existing rails)

### 1. `landing_page` — an 11th campaign asset
- Add `landing_page` to the `campaign_assets.kind` enum (additive) and to `DEFAULT_ASSET_PLAN` (positioned right after `offer` — it's the hub the ads point at). The kit is now 11 assets.
- Generated by a new house-rule-guarded prompt from the campaign offer → body JSON `{ headline, subhead, bullets: string[3..5], ctaLabel }` (ctaLabel defaults to "Register your interest"). Goes through `generateAsset` dispatch + the chat Approve/Go-again loop like every other asset. **House rules apply** (no price, no guarantees, no fabricated proof, register-interest CTA).
- `materialiseAsset` for `landing_page`: no external CMS row — returns null (the public route renders directly from the campaign + this asset). The "live" state is driven by campaign status (below), so nothing to materialise.

### 2. The public landing page — a dedicated branded route
- `src/app/site/[siteSlug]/c/[campaignSlug]/page.tsx` (public; host-resolved). Resolves tenant+site via the existing **`resolvePublicSite({ host })`** (control-plane `site_domains`), loads the campaign by `slug` **within that tenant**, and renders a **campaign-landing template** only when the campaign has an approved `landing_page` asset AND status ∈ {`ready` (preview), `active` (live)} — otherwise 404.
- **Branding from tenant settings, not scraped HTML:** the template pulls the tenant **logo** (`getChromeLogoSrc`/branding), **accent + theme** (appearance settings), **fonts**, and **business name/contact** — the same brand identity the app chrome + AI post-images already use. Layout: hero (headline/subhead on the accent), benefit bullets, the signup form, logo + contact, a plain footer. Clean, on-brand, reliable.
- The dev/preview URL is `/site/<siteSlug>/c/<campaignSlug>`; in prod it resolves on the client's mapped host (e.g. `theirdomain.ie/…`) exactly like the rest of the public CMS.

### 3. The signup form + host-scoped endpoint (secure by construction)
- **Form** (client component): `name`, `phone`, `email`, optional `message`, a **honeypot** field, and a **hidden `campaignSlug`** + the site's host is implicit. Posts to the endpoint below; on success shows an inline thank-you (no redirect needed).
- **`POST /api/campaigns/signup`** (public — added to middleware `PUBLIC_API_PREFIXES`, like `/api/leads/inbound`):
  1. Resolve tenant+site from the **request host** via `resolvePublicSite` (dev: accept `?site=`/a body `siteSlug`). No host → 400. **No API key anywhere** — the host is the tenant proof (control-plane `site_domains`, same trust basis as auth).
  2. Honeypot filled → silent 200 (drop). Rate-limit per IP (like `/api/leads/inbound`), 32 KB cap, validate name+one-of(email,phone).
  3. `runWithTenant(tenantId, …)`: verify a campaign with `campaignSlug` exists **in this tenant** (else 404 — can't post to another tenant's campaign), then `upsertLead({ fullName: name (split via humanName), email, phone, source: "landing", campaign: <campaign.name>, notes: message, sourceLeadId: <dedupe key> })`. Reuses the exact `upsertLead` the inbound webhook uses (fullName split, `source`+`sourceLeadId` dedupe, entry-stage assignment from the pipeline engine).
  4. Return `{ ok: true }`.
- **Tenancy:** the campaign-in-tenant check + `runWithTenant` make cross-tenant submission impossible; the per-tenant DB file is the structural guard.

### 4. Attribution → pipeline (already built)
- The lead lands with `campaign = "Summer Shape Up 2026"`, gets the entry stage (pipeline engine), and the board's **campaign filter** (from the pipeline-management work) segments it. Nothing new — Slice 1/pipeline already did this.

### 5. Launch + hub
- **Launch** (`launch_campaign`): in addition to publishing the blog + queuing email/social, flip the campaign `ready → active` (already happens) — which makes the landing page **publicly live**. Add the landing URL to the launch summary.
- **Campaign detail hub** (`/marketing/campaigns/[id]`): show the **landing-page URL** (with a copy + "view" link) once approved, and a **signup count** (leads where `campaign = campaign.name`) — the first hint of the Slice-3 CFA scoreboard.

## Security, tenancy, testing, rollout
- **Security:** no API key in public HTML (host = tenant proof); honeypot + rate-limit + validation + size cap; campaign-must-belong-to-resolved-tenant; the endpoint only ever creates a lead (low-blast write), mirroring `/api/leads/inbound`'s public posture.
- **Tenancy:** every write under `runWithTenant`; host→tenant via the trusted `resolvePublicSite`; per-tenant DB is the structural guard.
- **Metering:** the landing-copy generation is metered (agentKey `marketing`) like every other asset. No new AI cost surface beyond one more asset.
- **Tests:** pure tests for the landing prompt (house-rule clause + offer), the plan (11 assets, landing_page after offer), the signup validation/dedupe helpers, and the honeypot/host-resolution decision helper. Gate: typecheck + `npm test` + build.
- **Rollout:** additive — one enum value, one asset, one public route, one public endpoint (+ middleware prefix). No env. Existing campaigns (built pre-Slice-2) simply have no landing_page asset until rebuilt/regenerated. Deploy `railway up` from `app/`.
